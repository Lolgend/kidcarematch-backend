# Family Preference Profile Lifecycle and Schema Architecture

## Context

Parents evaluating preschool options in Singapore frequently need to search for multiple children concurrently (e.g., an infant requiring infant care and an older child needing kindergarten placement) or evaluate alternative search scenarios (e.g., prioritizing centres near the home residence versus centres near a workplace). Previously, KidCareMatch lacked a persistent multi-profile mechanism for parents to organize, store, and switch between distinct matching criteria scenarios. To deliver personalized recommendations for families with diverse childcare needs, the platform requires an authenticated multi-profile portfolio architecture with strict domain validation, composite uniqueness, and lifecycle ownership.

## Decisions

1. **Multi-Profile Portfolio Model (1-to-Many Cardinality)**: Rather than restricting each parent user to a singleton matching profile, `FamilyPreferenceProfile` models a 1-to-many relationship where each authenticated parent `User` can create, maintain, and switch among multiple named preference profiles. Profiles represent specific children (e.g., "Liam - Infant Care", "Maya - Kindergarten") or distinct commute scenarios (e.g., "Workplace Proximity Scenario").
2. **Composite Uniqueness on Profile Names**: Profile names are required and must be unique within each parent's account. This invariant is enforced at the database level by the composite unique constraint `uq_family_profile_user_profile_name` on `(user_id, profile_name)`. Submitting duplicate profile names returns HTTP 409 Conflict, preventing duplicate profile confusion while allowing different parents to use identical profile names independently.
3. **Canonical RESTful Collection and Member Routing**: Profile operations are mounted under the canonical prefix `/api/v1/profile`. Collection endpoints handle creation (`POST /api/v1/profile`) and listing (`GET /api/v1/profile`), while member endpoints manage retrieval, atomic replacement, partial update, and deletion (`GET/PUT/PATCH/DELETE /api/v1/profile/{profile_id}`).
4. **Strict Domain Validation & Invariant Enforcement**:
   - **Postal Code Anchors**: Residence and workplace postal codes enforce 6-digit Singapore postal code formatting (`^\d{6}$`). When location preference is set to `WORKPLACE` or `EITHER`, `workplace_postal_code` is mandatory; omitting it triggers HTTP 422 Unprocessable Entity.
   - **Normalized Enrollment Horizon**: Target enrollment months are accepted as `"YYYY-MM"` and persisted normalized to the 1st day of the specified month at 00:00:00 UTC, serializing back to client consumers as `"YYYY-MM"`.
   - **Balanced Trade-Off Weights**: Cost and travel trade-off weights (`cost_weight`, `travel_weight`) must be within `[0.0, 1.0]` and sum to `1.0` (`round(cost_weight + travel_weight, 2) == 1.0`).
   - **Financial and Demographic Bounds**: Non-negative household income (`household_income >= 0.0`), positive household member count (`household_member_count >= 1`), and positive maximum budget ceiling (`budget_max > 0.0`) are strictly enforced.
5. **Strict Role-Based and Ownership Authorization**: All profile endpoints enforce verified Firebase Bearer token authentication. Access is strictly restricted to active accounts with `role == UserRole.PARENT` (`get_current_parent`). Administrative accounts (`UserRole.ADMIN`) and suspended parent accounts (`AccountStatus.SUSPENDED`) are rejected with HTTP 403 Forbidden. Unauthenticated requests receive HTTP 401 Unauthorized. Member lookups strictly scope queries to the authenticated parent's `user_id`, returning HTTP 404 Not Found for non-matching or other parents' IDs to prevent enumeration leaks.
6. **Surrogate Key Identifiers & Cascade Integrity**: `FamilyPreferenceProfile` uses an auto-generated UUID surrogate primary key (`profile_id`). Foreign keys reference `User.user_id` with database-level `ondelete="CASCADE"` and ORM-level `cascade="all, delete-orphan"`, guaranteeing automated cascade deletion if a parent account is removed.
